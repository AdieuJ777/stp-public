# 双模式 Parity 审计（2026-11-03）

> 审计对象：`script.py`、`graph.py`、`plan.py`、`validation.py`、`executor.py` 与现有测试
> 基线：97 个测试全部通过（`python -m pytest -o addopts="" -q`，6.57s）
> 关联：README 的「核心概念 / 执行语义」与内部 ADR-000
> 性质：只读审计，未修改任何代码。

---

## 0. 结论摘要

1. **执行语义 parity 由架构保证**：脚本与图生成同一份 `TaskIR`，由同一个 `TaskRuntime` 执行，不存在第二条执行路径。
2. **编排表达力并不对等**：脚本 API 是受限前端（顺序 + 条件分支 + 自动汇合 + 单个 end），图 API 是完整 DAG 前端（显式节点/边/路由、多 end、共享节点、任意无环拓扑）。
3. **差分测试覆盖偏窄**：目前只覆盖“线性步骤”和“单层分支 + 汇合”，没有覆盖嵌套分支、空 case、多 end、错误路径、取消、超时和工具/LLM 步骤。
4. **建议把 parity 拆成五层分别验收**（见 §2），并在文档中明确“脚本表达力边界”，而不是追求所有拓扑在两端都能写出来。

一句话：

> **在“两端都能表达的计划形状”内，行为等价是架构保证的；“哪些形状只能图模式表达”目前没有清单；现有差分测试不足以证明等价覆盖。**

## 2. Parity 的五层定义

| 层级 | 含义 | 当前判断 |
|---|---|---|
| P-A 计划汇聚 | 两端都生成同一 `TaskIR` schema，走同一套静态校验 | ✅ 满足 |
| P-B 执行语义 | 相同输入 + 相同执行路径 → 相同状态、输出、错误码、调用次数 | ✅ 满足（同一 Runtime） |
| P-C 可观测 | 事件类型、`seq`、错误码、checkpoint 字段一致 | ✅ 满足（同一 EventBus / Store） |
| P-D 作者表达力 | 同一逻辑任务能否在两端都写出来 | ⚠️ 不对等，且边界未文档化 |
| P-E 差分证据 | 两端写同一任务并比较关键行为 | ⚠️ 只覆盖线性/单层分支 |

**关键区分**：P-D 不要求“脚本能表达所有 DAG”（那会变成“任意 Python 转图”）；它要求把“脚本能表达什么、不能表达什么”写成明确清单，并在重叠范围内用 P-E 证明等价。

## 4. 差异分类

### A. 架构允许、需要文档化的表达力差异

这些不是缺陷，但不能继续隐含在实现里：

- 脚本是“顺序 + 分支 + 自动汇合 + 单 end”的受限前端；
- 图形 API 可以表达多 end、共享节点、菱形、任意无环 DAG；
- 脚本分支会自动生成 `join`，图模式不一定有 `join`，因此“同一逻辑任务”的 IR 形状可能不同；
- 脚本禁止在分支 case 内调用 `end()`，图模式允许分支直接路由到 end。

**处理方式**：在本文件与 ADR-000 中声明“parity 以可观察行为为准，不以 IR 形状为准”；把图模式独有能力单独列出，不要求脚本补齐。

### B. 需要补测试的差异

以下能力在两端都已实现，但没有差分证据：

- 工具步骤、LLM 步骤（现有差分只用了 `func=`）；
- 嵌套分支、空 case；
- 错误路径：工具失败、模型失败、结构化输出失败；
- 重试次数与最终失败状态；
- 取消、步骤超时、任务超时、步数/模型调用限制；
- 非线性恢复（现有脚本/图恢复等价用例是线性任务）。

### C. 需要决策的差异

- 图模式独有的控制流（多 end、共享节点、菱形）是否需要脚本等价物？当前答案是“不需要”，但必须在文档里写死。
- 脚本是否应该提供 `ctx.join()` / 多 end 支持？在 P1/P2 范围内建议不做，避免脚本 API 变成半个图 API。

## 5. 缺口清单

| 编号 | 缺口 | 影响 | 建议 |
|---|---|---|---|
| G-01 | 无嵌套分支 parity 测试 | 复杂 DAG 行为未证明 | 补一个两层 branch 用例 |

## 6. 建议补充的最小测试集

按性价比排序，预计 1–1.5 天：

1. `test_nested_branch_parity`：两层 branch，比较输出、工具调用序列、错误码。
2. `test_tool_failure_parity`：工具抛 `ToolCallError`，比较 `E_TOOL_CALL`、重试次数、最终状态。
3. `test_llm_step_parity`：MockLLM 返回结构化结果，比较输出与 `LLM_CALL_END` 次数。
4. `test_empty_branch_case_parity`：空 case 路由到 join。
5. `test_cancellation_parity`：运行中取消，比较 `E_CANCELLED` 与未闭合工具调用。
6. `test_graph_multiple_ends`：图模式多 end，只验证图模式自身行为。
7. `test_graph_shared_node_diamond`：图模式共享节点，只验证图模式自身行为。

> 第 6、7 项不是 parity 测试，而是“图模式独有能力”的回归测试；应放在 `test_executor.py` 或新文件 `test_graph_only.py`，避免污染 parity 用例。

---

## 7. 结论

- **P-A/P-B/P-C 已经成立**，这是项目最重要的资产：两端共享 IR 和运行时。
- **P-D 的边界必须在文档里说清楚**：脚本不是图的全集，图模式独有能力不等于“脚本模式缺失”。
- **P-E 是当前最薄的一层**：现有差分测试只够支撑“线性/单层分支等价”，不足以支撑“所有受支持计划等价”。
- 0.3.0 的 parity 门槛应该是：**§6 的 1–5 项通过 + 本矩阵随代码同步更新**。

## 8. 维护方式

- 新增任何控制流/能力时，先在本矩阵加一行，标明脚本/图/运行时/差分测试四列；
- 若只支持单模式，必须在“备注”写 `experimental` 并给出理由；
- 每次发版前跑一遍 §6 的测试集；
- 本文件是 ADR-000 的执行清单，不是一次性报告。
