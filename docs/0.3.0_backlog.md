# 0.3.0 可信执行债务清单（按优先级）

> 基线：2026-11-04，112 个测试通过（P0 修复 + parity 最小集）
> 来源：内部路线图 §2.2、§9 Sprint 1；`dual_mode_matrix.md`；`p1_evidence_recheck.md`
> 定位：0.3.0 的唯一目标是**修正确性与安全债**，不是加控制流。
> 原则：**先让已有能力可信，再让新能力出现。**

---

## 0. 优先级口径

| 级别 | 含义 | 处理要求 |
|---|---|---|
| **P0** | 会产生错误结果、重复副作用、阻塞运行时或泄露数据 | 0.3.0 必须关闭，否则不发布 |
| **P1** | 影响 API 可信度、恢复正确性或可诊断性 | 0.3.0 应关闭；确有困难需写明延期理由 |
| **P2** | 性能、工程化、发布治理 | 可与 0.3.0 并行，不阻塞发布 |

排序依据不是“改动大小”，而是：**错误后果 > 安全 > 并发正确性 > API 诚实 > 可诊断性 > 工程化**。

## 2. P0：不修就不能发 0.3.0

> 2026-11-03：B-01～B-04 全部关闭；2026-11-04：补齐 parity 最小集，112 个测试通过。

### B-01 幂等键跨尝试不稳定（✅ 2026-11-03 已修复）

- **现象**：`ExecutionContext.call_tool()` 每次调用生成新的 `call_id`，`idempotency_key = f"{run_id}:{call_id}"`（`stp/context.py:467-473`）。重试或恢复后键会变。
- **影响**：工具侧无法用幂等键去重；`at-least-once + 幂等契约` 在修复前不成立。
- **修复**：`idempotency_key` 改为 `lineage_id:node_id:step_index`。`TaskRun` 与 `Checkpoint` 增加 `lineage_id`，恢复链沿用首次运行的标识，因此跨重试、单次恢复和链式恢复都稳定；`call_id` 仅保留为单次调用的诊断 ID。
- **验收**：
  - 同一节点重试两次，`idempotency_key` 相同；
  - 不同节点键不同；
  - 恢复前后同一逻辑步骤键相同；
  - 链式恢复（多次 resume）键仍然相同；
  - 事件里同时保留 `call_id` 和 `idempotency_key`。
- **测试**：`test_idempotency_key_is_stable_across_retries`、`test_idempotency_key_differs_per_node`、`test_idempotency_key_is_stable_across_resume`、`test_idempotency_key_is_stable_across_chained_resumes`。
- **注意**：如果后续要支持循环，`step_index` 需要替换为“迭代感知”的逻辑 ID；当前按 DAG 语义实现。

### B-02 同步 callable 阻塞事件循环（✅ 2026-11-03 已修复）

- **现象**：`ExecutionContext.call_function()` 直接调用 `func(input_data)`（`stp/context.py:551` 附近），`FunctionTool.execute()` 同样直接调用同步函数（`stp/tools.py:59` 附近）。
- **影响**：同步函数执行期间整个事件循环停摆；步骤超时、任务超时、取消都无法生效。这在真实工具（文件、网络、CPU 计算）上会直接暴露。
- **修复**：
  - 同步函数用 `asyncio.to_thread()` 执行；async 函数保持直接 `await`；
  - 同步函数返回 awaitable 时再 `await`，兼容 callable object / partial；
  - 步骤/工具超时仍由外层 `asyncio.wait_for` 控制。
- **验收**：
  - 同步函数阻塞 200ms 时，事件循环心跳仍能推进；
  - 同步函数超时能被 `E_STEP_TIMEOUT` 捕获；
  - async 函数行为不变；
  - `FunctionTool` 的同步实现同样不阻塞。
- **测试**：`test_sync_function_does_not_block_event_loop`、`test_sync_function_step_timeout_is_enforced`、`test_function_tool_sync_does_not_block_event_loop`。
- **限制**：线程无法被强制终止；步骤超时后同步函数可能仍在后台完成，有副作用的同步逻辑应改为 async 工具或幂等工具。

### B-03 checkpoint 明文保存 input/state（✅ 2026-11-03 已修复）

- **现象**：`_save_checkpoint()` 直接写入 `snapshot["input"]` 和 `snapshot["state"]`（`stp/executor.py:461-495`），`Checkpoint` 模型也是明文 `dict`（`stp/checkpoint.py:78-79`）。事件 payload 有 `redact()`，checkpoint 没有。
- **影响**：任务输入或步骤输出里的 API Key、PII、令牌会原样落盘。P1 的 NFR-004 “不记录密钥等敏感凭据”在修复前只对事件成立。
- **修复（采用加密落盘）**：
  - `JsonCheckpointStore` 默认使用 AES-GCM 加密，文件仍是 JSON 信封（`format/nonce/ciphertext`）；
  - 密钥优先级：`STP_CHECKPOINT_KEY` 环境变量 → 构造函数 `encryption_key` → `base_dir/.checkpoint.key`（自动生成，0600）；
  - 检查点文件 0600、run 目录 0700（Windows 上 chmod 能力有限，失败不阻断）；
  - 旧明文检查点仍可读取；新写入默认加密；
  - `encrypt=False` 显式降级为明文，仅用于调试/迁移。
- **不要做**：对恢复所需的 `state` 做单向 `redact()`——那会让恢复后的状态失真，属于错误设计。
- **验收**：
  - checkpoint 文件中不出现测试用秘密标记；
  - 错误密钥明确失败；
  - 加密文件在未启用加密的 store 中读取时明确失败；
  - 旧明文检查点仍可恢复。
- **测试**：`test_checkpoint_is_encrypted_on_disk`、`test_checkpoint_wrong_key_is_rejected`、`test_checkpoint_encrypted_file_requires_key`、`test_checkpoint_encryption_can_be_disabled`、`test_encrypted_store_reads_legacy_plaintext_checkpoint`、`test_checkpoint_store_generates_local_key_by_default`。
- **限制**：本地 key 文件是“防误传/误备份”级别，不等同于 KMS；跨机器共享检查点应使用独立密钥并考虑轮换。

### B-04 单 runtime 并发 run 互相覆盖事件（✅ 2026-11-03 已修复）

- **现象**：`TaskRuntime.last_bus` 是实例级共享状态（`stp/executor.py:75-79`），`last_events` 只返回最近一次 run 的事件。
- **影响**：同一 runtime 并发跑两个任务时，调用方拿不到各自的完整事件；后续 checkpoint/观测会串。0.5.0 的并行/多 run 会直接踩雷。
- **修复（非破坏性）**：
  - 新增 `TaskRuntime.events_for(run_id)`，按 run 返回完整事件流；
  - 内部用 `_buses: dict[run_id, EventBus]` 保存，`last_events` 保留为兼容层；
  - 新增 `forget_run(run_id)` 与 `max_retained_runs`（默认 128）避免无限增长；
  - `resume` 产生的新 run 同样按自己的 `run_id` 隔离；
  - 未改成 `run()` 返回 `RunResult`，避免破坏现有 API；完整句柄留到 0.4.0。
- **验收**：
  - 并发两个 run，各自事件只包含自己的 `run_id`；
  - `last_events` 仍可用，但只代表最近一次；
  - `resume` 前后事件隔离；
  - 超出保留上限时旧 run 事件被释放。
- **测试**：`test_concurrent_runs_do_not_share_events`、`test_events_for_unknown_run_is_empty`、`test_forget_run_releases_only_that_run`、`test_retained_run_events_are_bounded`、`test_resume_events_are_isolated_from_original_run`。

## 3. P1：影响可信度与验收

### B-05 公共 API 字段“声明但未生效”

- **涉及字段**：
  - `RetryPolicy.retryable_errors`（`models.py:30`）——执行器未使用；
  - `ToolSpec.supports_cancellation`（`models.py:234`）——运行时不传播取消；
  - `ToolSpec.allow_concurrent`（`models.py:236`）——未使用；
  - `ToolSpec.required_permissions`（`models.py:237`）——未校验；
  - `PauseToken` / `PAUSED`——占位。
- **影响**：用户会以为有保护，实际没有。这是“公共 API 说谎”，比缺功能更伤信任。
- **修复**：每个字段三选一——**实现 / 从公开 API 移除 / 标记 experimental 并在文档中说明不生效**。
  - `retryable_errors`：接入 `_can_retry()` 判断；
  - `supports_cancellation`：要么接入取消传播，要么标 experimental；
  - `allow_concurrent`、`required_permissions`：0.3.0 建议移除或标 experimental，等权限模型落地再实现；
  - `PauseToken`：保留但明确标注 P2 占位，不作为公开承诺。
- **验收**：`grep` 公共模型字段，每个都有“实现/experimental/移除”结论；文档同步。
- **测试**：至少覆盖 `retryable_errors` 生效与不生效两种分支。

### B-06 静态校验补全

- **缺口**：
  1. `end.output_mapping` 的引用未校验（`validation.py:222` 只遍历 `input_mapping`）；
  2. 数据流顺序未校验：引用了某路径上尚未产生的 `state` key；
  3. 工具 action 未校验工具是否在注册表中（执行时才报 `E_TOOL_CALL`）；
  4. `max_steps` 静态口径只数 `step` 节点，运行时 `branch` 也计数（`validation.py:82` vs `executor.py` 的计数逻辑）。
- **修复**：逐项补规则；统一 `max_steps` 口径（建议静态也计 branch，或运行时不计 branch，二选一）。
- **验收**：错误引用、未注册工具、顺序倒置、`max_steps` 边界都能在 `validate_plan()` 阶段失败，错误码 `E_PLAN_INVALID`。
- **测试**：4 个负例 + 1 个 `max_steps` 边界正例。

### B-07 恢复不感知代码实现变化

- **现象**：`plan_hash` / `spec_hash` 是结构哈希（`checkpoint.py:44-50`），不包含函数体、验证器、分支条件实现。
- **影响**：改了函数实现但结构未变时，恢复会用新代码跑旧状态，结果可能不一致。
- **修复**：`TaskSpec` 增加 `code_revision`（字符串或 git commit），checkpoint 写入并校验；不一致拒绝恢复，错误码 `E_CHECKPOINT_INCOMPATIBLE`。
- **验收**：改变 `code_revision` 后 resume 被拒绝；未改变时正常恢复。
- **测试**：`test_resume_rejects_code_revision_change`。

### B-08 checkpoint 无保留策略

- **现象**：每个 step 一个文件，长期运行无限增长。
- **修复**：`max_checkpoints_per_run`（默认如 20）与/或 TTL；写入后清理旧文件；清理失败只告警不失败任务。
- **验收**：超过上限后最旧检查点被删除；最新检查点仍可加载；清理失败不破坏当前检查点。
- **测试**：`test_checkpoint_retention_keeps_latest`。

### B-09 LLM 400 全量回退 json_object

- **现象**：`_is_unsupported_response_format()`（`stp/llm.py:311-314`）把任何 `status == 400` 都当作“不支持 json_schema”，触发回退。
- **影响**：认证错误、请求格式错误、schema 错误会被吞掉并换一种请求重试，掩盖真实原因。
- **修复**：只匹配明确的“不支持 response_format / json_schema”错误消息或错误码；其他 400 直接抛 `ModelCallError`，保留原始错误。
- **验收**：400 认证错误不回退；明确 unsupported 错误才回退一次。
- **测试**：两个 fake 异常分别验证。

### B-10 双模式差分测试覆盖不足（✅ 2026-11-04 已修复最小集）

- 已补：

  2. `test_tool_failure_and_retry_parity`（错误码 + 重试次数）；
  3. `test_llm_step_parity`；
  4. `test_empty_branch_case_parity`；
  5. `test_cancellation_parity`；
  6. `test_graph_multiple_ends_selects_active_end`（图模式单测）；
  7. `test_graph_shared_node_diamond_runs_once`（图模式单测）；
  8. `test_branch_resume_parity`（单层分支恢复，补齐 FR-029）；
  9. `test_graph_branch_resume_route_mismatch`（图模式路由变化拒绝恢复）；
  10. `test_step_timeout_parity`；
  11. `test_task_timeout_parity`；
  12. `test_model_call_limit_parity`；
  13. `test_max_steps_limit_parity`；
  14. `test_nested_branch_resume_parity`（嵌套分支恢复）；
  15. `test_graph_multiple_ends_resume`（图模式多 end 恢复）。
- **剩余**：非幂等副作用、模型失败的 parity，列入 0.4.0 前的补充项。
- **验收**：1–5 通过；矩阵表同步更新。

## 4. P2：可以做，但不阻塞发布

### B-11 事件同步落盘、无批量

- `JsonlEventStore` 每条 flush、`SqliteEventStore` 每条 commit；NFR 要求“批量、不阻塞步骤”。
